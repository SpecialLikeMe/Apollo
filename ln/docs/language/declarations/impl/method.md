# Method declaration — implementation

## Grammar surface

From `Apollo-Main/compiler/compilerv1.g4`:

```antlr
methodDecl
    : (STATIC | VIRTUAL)? returnType ID '(' params? ')' attributeBlock? block
    ;
```

`methodDecl` is reachable only from inside `classBody`. The grammar enforces that `static` and `virtual` cannot appear together — they are alternatives in the same modifier slot.

## Parse tree shape

A `MethodDeclContext` exposes:

- `STATIC()` / `VIRTUAL()` — optional terminal tokens, at most one present.
- `returnType()`, `ID()`, `params()`, `attributeBlock()`, `block()` — the same accessors as `function`.

The method's parent in the tree is a `ClassBodyContext`, which gives the visitor enough context to know which class owns the method and what visibility section it sits under.

## Frontend validation

`Apollo-Main/compiler/cpp/src/apollo_runtime.cpp` validates a method by:

1. Building the implicit `self` parameter when the method is non-static. The receiver type is the owning class; the borrow flavor is determined in a later pass.
2. Validating the parameter list and return type using the same logic as for top-level functions.
3. Walking the body. Field references through `self` are resolved against the owning class's field list. Method calls through `self` resolve against the class's method list.
4. After walking the body, determining the receiver's borrow flavor: mutable if the body assigns to any field through `self`, immutable otherwise.
5. Recording the method in the class's method table with its signature, visibility, and static/virtual flag.
6. For `virtual` methods, also recording the method in the vtable layout for any interface the class satisfies.

## Lowering

In `Apollo-Main/compiler/cpp/src/visitor.cpp`:

1. The method lowers to an LLVM function. For non-static methods, the first parameter is a pointer to the class struct (the `self` receiver). For static methods, no receiver parameter is emitted.
2. The function name is mangled to include the class name to avoid collisions across classes.
3. The body is lowered using the same statement/expression lowering as for top-level functions. References to `self.field` lower to `getelementptr` on the receiver pointer.
4. Direct method calls lower to direct LLVM calls. Interface-dispatched calls (through `InterfaceName&`) lower to vtable indirect calls using the recorded method slot.

## Runtime support

Static and instance methods need no runtime support beyond standard function-call ABI. Virtual dispatch through an interface uses a per-class vtable generated by the lowering pass and held in static data; the dispatch helpers live with the runtime objects under `Apollo-Main/compiler/runtime_support/`.

## Edges and gotchas

- The frontend infers `self` mutability from the body, not from any explicit annotation. There is no way to mark a method "const" at the source level — if the body does not write, the receiver is immutable.
- Two methods on the same class cannot share a name. There is no overloading.
- A virtual method on a non-interface-implementing class is allowed but has no special dispatch effect — calls always go direct because there is no vtable involved.
- Methods inherit the class's generic parameters automatically. A method on `Stack<T>` can mention `T` in its signature and body.
- `self` cannot be reassigned and cannot be moved out of. It is always a borrow.
